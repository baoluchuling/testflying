# Connector 交付与失败协议

仅在截图 Connector 任务中使用本协议；普通本地采集仍按主工作流交付原图。

先调用 `get_capture_task({})`，核对平台、包名、原始提示词、目标顺序及 `requiresFinalization`。每个 target 是独立目标，不能按设备、语言和页面另行展开组合。原始提示词规定画面要求；任务身份和目标索引以工具返回为准。

## 以目标画面决定操作范围

原始提示词规定需要呈现的页面和状态，不隐含全面功能验收。可关闭的非目标弹层先关闭并返回目标页；无关功能异常、可选数据为空等，只要不妨碍目标画面，就不作为失败、暂缓或修复的前置条件。画面符合要求后采集并推进，不继续探索无关操作。真实目标内容缺失、导航受阻或明确要求的功能状态未达到时，才针对该阻碍恢复／修复，并沿用下文两次首轮与延后补拍流程。不要通过隐藏目标内容、替代页面或伪造数据满足要求。

## 顺序首轮与延后补拍

在当前会话按原 `targetIndex` 维护目标进度、完整尝试次数、暂缓原因和已尝试的恢复办法，不修改原始目标数组。

1. **首轮依序推进。** 按 A → B → C 的原目标顺序逐项处理。一个目标成功取得合格候选图后就继续下一项；上传后的候选图仍需遵守最终审阅协议。
2. **首轮每项目标最多两次完整尝试，包含第一次。** 一次尝试是实际准备／进入目标页、等待就绪、检查要求并尝试采集的完整过程，不是一次点击或工具调用。第一次失败后，针对真实原因做恢复或修复，再进行第二次；等待、普通操作及同一上传的确认重试不另算一次截图尝试。
3. **两次未成就暂缓。** 如果 B 两次仍无法采集或无法满足画面要求，记录 B 未完成及具体原因，继续 C。暂缓不等于完成、不删目标、不缩小总数，也不将整个 Goal 标为 blocked 或调用 `report_capture_failure`。首轮尚有未处理的目标时，不提前回头反复处理 B。
4. **清理可确认的候选图再换目标。** B 有不合格本地图或已确认上传的候选图时，先用实际 ID 和索引执行 `discard_screenshot`，确认撤销后再切换。上传、撤销或最终提交结果未知时，必须先确认同一操作，不能用“跳过页面”绕过未知交付状态。
5. **全部走一遍后再回补。** 首轮结束后，按原顺序处理暂缓项，分析原因、修复并重试。能修复就继续完成；某项连续无进展时先处理其余欠项，有具体的新恢复办法才再尝试，不能原样无限重复同一个失败状态。保持原应用、语言、设备及画面要求。
6. **最后再决定整单结果。** 所有目标和候选图都合格后才按下文最终提交。如果其他可执行目标均已处理，剩余项也已实际尝试修复仍确认无法完成，才报告未完成目标、实际阻塞及已试办法；预算耗尽也结束为失败。确实无法恢复、阻断所有目标的共同环境问题仍按阻塞协议处理，不能把局部页面失败误报为全局阻塞。

## 候选图与重拍

- 使用当前节点提供的 `validate_simulator`、`capture_screenshot`、`upload_screenshot`，保留实际截图 ID 与零基 `targetIndex`。Skill 自带 runner 或助手可用于准备、导航和检查；Connector 任务的正式交付仍走 Connector 工具。
- `get_capture_task` 中的 `pendingScreenshot` 是当前本地图；`uploadedScreenshots` 是已确认上传的候选图。原图审阅不合格时，如节点提供 `discard_screenshot`，按对应 ID 和索引丢弃，再调整页面、重新采集和检查；已确认上传的候选图也可在最终提交前撤销。
- 上传已经开始或结果未知时，先用同一个 screenshotId 重试 `upload_screenshot` 确认结果。撤销结果未知时先重试同一次撤销；最终提交结果未知时先重试最终提交。不能换 ID 重放未知上传，也不能把未知结果当作失败。
- `requiresFinalization=true`：所有图上传后仍只是候选图。逐张审阅、补拍合格后调用 `finish_capture_task({})`；只有其 `delivered=true` 才完成整单。最终提交开始后不再改图。失败整单不会把未最终提交的候选图回传外部。
- `requiresFinalization=false`：沿用节点的旧交付协议，以 `upload_screenshot` 返回 `delivered=true` 为完成；不要调用节点未提供的工具，也不要尝试撤回已经完成回传的历史任务。

## 阻塞与失败原因

构建、安装、启动或普通命令失败是排查线索，不能据此直接结束整单。允许按任务需要修改项目源码、依赖和构建配置，保护不相关的用户改动；分析实际诊断、修复问题并重试，在同一 Goal 内继续原目标。修复仍须保持真实 App 行为和画面要求，不能用 Mock 或替代画面掩盖故障。执行预算内持续处理可恢复的问题，只有实际尝试后确认无法继续，或执行预算耗尽，才失败。

可恢复的工具错误在当前 Goal 内继续修复或等待重试。没有现成模拟器时自行准备或创建；缺开发工具或运行时时先尝试补齐，不能仅因找不到现成设备就失败。实际尝试后，仍因开发环境、运行时、必要凭据或其他明确阻塞无法完成时：

1. 如果提供 `report_capture_failure`，调用 `report_capture_failure({"reason":"实际阻塞事实、已尝试的处理及仍缺少的条件"})`。原因写简洁、具体的自然语言，区分已确认事实和不确定信息。该工具是确定终止任务；不要为可恢复错误调用它。
2. 原因不得包含完整提示词、密钥、Token、Cookie、签名 URL、私有目录或大段日志。不能把最后看到的错误猜成根因。上传、撤销或最终提交还未确认时，先解决该操作；节点会拒绝用失败上报覆盖未知交付。
3. 旧节点未提供该工具时，在当前会话明确说明实际阻塞，再按已有工具结果结束；不要虚构工具或声称中心已经收到详细原因。

不要在未获得最终交付确认时主动把 Goal 标成 complete。中心的新查询和失败回调以 `errorCode` 保存稳定错误码，`error` 按“任务结果；已确认候选图 x/y；具体原因”显示脱敏说明；没有原因则为“未提供具体原因”。Goal、RPC、退出码等技术上下文保留在节点和中心日志，不拼进外部详情，不能承诺还原历史根因。
